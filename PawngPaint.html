Exploring Mechanics Through Pawng

Starting with a simple paddle-and-ball game, I explored how a small set of familiar parts could lead to new rules, player choices, and prototypes.

Timeline

1 week

Technologies

Unity, RenderTexture

Project Overview

A two-player Pawng experiment where the ball paints the arena in each player color, turning the ball path into persistent territory and the final score.

Watch the Prototype

Starting with a small scope

I wanted to make something simple enough to finish, but flexible enough to explore. I looked at IO games for inspiration: repeated shapes, minimal visuals, and straightforward mechanics that could be extended. I was also following the class readings and tutorials and wanted to build on physics, object tags, scoring, and sound.

When I felt stuck choosing a new idea, I returned to Pawng and asked how its basic elements could change. I considered painting the arena like a 2D territory game, capturing area instead of scoring points, making the ball feel like basketball keep-up, turning the paddles into goals for a football-like game, or asking players to avoid the ball. A reading about recording and displaying Boids motion paths led to the idea I chose: make the ball's path itself the important element.

Experiment 1: Ball Paint

Two players rally across a dark arena. The first ball path uses the background color; whenever a paddle hits the ball, the trail changes to that player's color. All four arena walls block the ball so the match stays inside the drawing space. When the timer ends, the game calculates each player's color coverage and shows the winner.

Questions I used to shape the rules

I listed uncertainties instead of deciding every rule in advance. Should the ball have gravity, curve, or speed up after repeated hits? Should a new ball appear periodically? Should the paddle stay rectangular or become a circle or triangle? Could it move horizontally as well as vertically? Should paddles collide? Which controls would work if more players joined? I left ideas such as curves, multiple balls, and more complicated controls as possibilities for later testing rather than adding them all at once.

Testing the basic setup helped settle some choices: I kept a single ball, made the walls bounce it back into the arena, and used a black background so both player colors would read clearly. I planned the color distribution for the end of the match rather than keeping a percentage display onscreen throughout play.

Technical tests and fixes

I started with a Trail Renderer. It produced a trail visually, but it did not record the path into the arena background as persistent paint, so it could not support the territory score I wanted. I switched to a RenderTexture.

The screen began lagging after only one hit. I traced the issue to reading the RenderTexture with ReadPixels every frame. Removing that call and calculating the color distribution only at the end made the prototype run much better. A separate color-format issue made every player's trail appear red; changing the RenderTexture format to A2B10G10R10 fixed the assigned colors.

I also found that the game kept simulating after the timer ended. I stopped the ball, enlarged the result text, and added a semi-transparent result panel. Because the winner was otherwise difficult to identify, I added the winner's player color to the result panel.

The important technical lesson was to make the visual trail persistent without repeatedly reading the full texture during play.

What I set out to test

The mid-prototype goal was to test whether the ball path could be recorded as color and whether the territory score could be calculated. I also checked how physics, visual feedback, and the result panel connected as a complete short match.

I used the prototype to answer a focused question: could the ball path persist as color and produce a readable score?

Small implementation checks

While debugging, I noted a few setup details that repeatedly mattered: confirm textures are assigned, connect the canvas to the camera, check that scene objects are linked, import TMPro when using TMP_Text, and put scripts on an appropriate object (creating an empty object when a script does not belong to a visible object).
